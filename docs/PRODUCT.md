# 产品决策记录

## 目标用户与问题假设

主要用户是独立开发者、小型外包工作室负责人。他们承接网站或小程序，沟通分散，范围常变化；需要一份能回到原话的需求基线。

围绕这一场景，已完成真实 AI 流程验证、首轮小规模评测与目标用户试用。产品继续通过实际任务反馈检验使用价值；用户规模、付费意愿和效率提升等结论以对应的研究与测量记录为准。

## MVP 的成功任务

用户无需知道提示词或数据库结构，能完成：保存初次沟通 → 审核需求及排除项 → 修改后确认 V1 → 只选第二次沟通 → 判断“原来不做会员，现在要会员” → 形成 V2 并查看前后对比。

需求采纳者是项目负责人；客户沟通来源是证据，不等于已签署合同。客户侧确认不在当前 MVP 范围内。

## 为什么这样设计

| 决策 | 原因 | 代价或边界 |
| --- | --- | --- |
| AI 候选由人确认 | 客户原话含设想、否定与未决问题，错误自动执行会改变范围 | 增加审核时间，需要测量总效率 |
| 引文逐字校验 | 把“有来源”变成可执行规则 | 不保证语义蕴含；需人工评测 |
| 范围变化关联稳定需求 ID | 修改排除项时保留同一条需求的演变 | 一条需求的粒度需要一致 |
| 版本快照不可覆盖 | 已确认内容可回溯，方便审查变化 | 版本越多存储越大 |
| 没有实际变化不生成新版本 | “忽略全部”和“未变”也是有效审核结果 | 审核记录与版本记录需分别理解 |
| 模型能力由部署管理员显式配置 | 避免不支持 JSON Schema 的服务商意外失败或静默改变行为 | 管理员需要了解服务支持情况，业务用户无需配置 |
| 正式工作空间与培训入口分离 | 业务页面聚焦实际模型结果与项目任务，固定案例只用于培训 | 部署管理员负责模型接入与权限配置 |
| 智能建议与手动维护共用版本流程 | AI 生成候选，人工补充和修订，统一保留原文证据及确认记录 | AI 建议仍需负责人审核，人工新增与模型生成应如实区分 |
| 原生 JS + SQLite | MVP 的规模不需要构建工具和独立数据库服务 | 后续协作规模大时需演进 |

## 数据与 AI 流程

```text
所选原文 + 项目上下文 / 版本基线
    ↓
提示词版本 + JSON Schema → 模型调用（至多一次重试）
    ↓
类型、原文引用、需求关联校验
    ↓
可编辑草稿 / 可审核变更 → 人工修改与确认
    ↓
事务检查修订与基线 → 正式版本 + 原文证据 + 审核记录
```

正式模式通过所配置的模型服务处理选中材料；独立培训入口明确标注演练。材料先归档再分析，生成候选后由人审核；模型调用计量留在后台记录，不展示在普通业务页面。模型不设置客户已同意结论、不编造报价工期、不直接更新正式版本。

## 已完成验证与迭代依据

- 已完成真实模型参与的需求提取与变更比较流程验证。
- 已完成首轮小规模评测与人工审核。
- 已完成目标用户试用，后续迭代以评测和试用反馈为依据。

方法与证据边界见 [评测说明](../EVALUATION.md)。后续工作是优化现有流程、扩充回归案例，并按实际需求决定客户确认链接、报价影响估算和聊天工具导入的优先级。

当前不主张为了展示技术而增加多 Agent、RAG 或复杂权限；新增能力应对应经过验证的任务。
